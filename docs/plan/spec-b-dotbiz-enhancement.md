## 1. 배경과 목적

### 1.1 문제 인식

1. **물량의 API 편중**: 현재 거래 물량은 **대부분 API 연동 고객**에서 나온다. 닷비즈(직접 사용 채널)의 기여도가 작아,
   채널이 한쪽에 쏠려 있고 닷비즈의 성장 여력이 활용되지 못하고 있다.
2. **닷비즈 직접 사용의 불편**: 닷비즈를 쓰는 셀러 OP들은 검색·예약 과정의 자잘한 불편
   (느낌상 멈춘 검색, 과거 날짜 실수, 룸 구성 변경 불가, 견적 재입력 등)을 겪는다 — 신규 고객사 유입과 사용 확대의 걸림돌이다.

### 1.2 목적

> **닷비즈를 사용하면서 불편한 점을 하나씩 개선해 고객 친화적인 플랫폼을 만들고,
> API 고객 물량이 대부분인 상황에서 닷비즈 고도화를 통해 닷비즈 고객을 추가로 확보하고 물량도 크게 늘린다.**
>
> ※ API 고객을 닷비즈로 이관시키는 것이 아니다 — **닷비즈 채널 자체를 키워** 고객사 확보와 물량 확보를 동시에 달성한다.

| 축 | 내용 |
|----|------|
| 고객 친화 | 현장 OP가 매일 쓰는 화면의 불편을 백로그로 수집해 순차 제거 |
| 고객사 확보 | 쓰기 좋은 포털·다국어·매뉴얼·복지 혜택으로 **신규 셀러 유입** 및 온보딩 장벽 완화 |
| 물량 확대 | 기존 닷비즈 고객의 사용 빈도·예약 건수 증대 → **닷비즈 채널 물량 성장** |

### 1.3 기획서 ①과의 관계

AI 요금 검색(트랙 A)은 **차별화 신기능**, 본 기획(트랙 B)은 **기본기 강화**다.
트랙 B는 ELLIS API·LLM 없이도 배포 가능하며, 트랙 A 파일럿의 성공 전제(쓸만한 포털)를 만든다.

## 3. 운영 방식 — 불편 개선 백로그

**프로세스**: 현장 지목(스크린샷/한 줄 요청) → 실사이트 대조 → 프로토타입 구현·검증 → 당일 배포 → 라이브 확인.
한 번에 크게 고치지 않고, **하나의 불편 = 하나의 커밋 = 당일 반영**을 원칙으로 한다.

**고도화 표기 (2026-07-17 도입)**: 닷비즈 원본과 다른(고도화된) 지점에는 화면에 보라색 **`UP` 배지**를 표기한다 —
마우스 오버 시 어떤 고도화인지 툴팁으로 설명되어, 기획자가 데모만 보고도 원본과의 차이를 한눈에 파악할 수 있다.
헤더의 **✨ 버튼**으로 전체 표기를 켜고 끌 수 있다(끄면 순수 클론 화면 — 설정은 localStorage 유지).
실사이트에 원래 있는 기능을 따라 만든 것(패리티)에는 배지를 달지 않는다.

#### 4.3.1 적립 규칙 정의 (현업 재정의 2026-07-29)

**① 적립 대상 조건**
- 닷비즈 생성 예약이 **투숙 완료**(check-out 경과) **AND 지불 완료(Fully Paid)**된 건. 상태 Confirmed. **취소·노쇼·환불 제외.**
- **지불 완료 조건**(현업 2026-07-29): 체크아웃 기준이라도 **지불 완료된 건만** 적립. 선불 업체는 체크아웃 시점에 이미 완료, 후불 업체는 **체크아웃 후 지불 완료 시점**에 적립. 투숙 완료·지불 미완결 건은 **‘적립 예정(지불 대기)’**로 분리 표시(`computePending`).
- **적립 내역 ↔ Bookings 연동**: 적립/예정 행에 **예약 코드(ELLIS)** 표시, 클릭 시 Bookings로 이동해 해당 예약 상세 표시. 오피포인트·부킹스는 **동일 예약 데이터(SEED_BOOKINGS)**에서 파생 → 코드로 상호 확인.

**② 적립 공식 — 예약금액의 %만 (기본·보너스 없음)**
- `포인트 = KRW환산(예약금액) × 기본요율% × 배수 ÷ 1,000` → **1 오마이포인트 = 1,000원 value**.
- 검산: 140,000원 × 1% ÷ 1,000 = **1.4 P** (현업 예시 일치).
- **다통화 환율 적용** — 예약통화(JPY 등)를 KRW로 환산 후 산출. 환율표는 `opPoints.ts`의 `FX_TO_KRW`(USD 1,480 · JPY 9.3 등, 2026 근사).

**③ 지정 호텔 배수 프로모 (ELLIS 내부 관리)**
- 특정 호텔은 기본요율의 **배수**로 적립(예: 기본 1% → 소테츠 신주쿠 1주간 1.5% = **배수 1.5 = 150%**).
- **ELLIS 내부 시스템에서만 변경.** 적용 범위 = **지정 호텔 · 기간(예약일 기준) · 지정 룸타입 · 지정 레이트플랜.** 데이터: `mocks/opPointsPromos.ts`(`{hotelId, roomType, ratePlan, start, end, multiplier, active, image?}`).
- **고객은 요율을 모른다** — 목록/검색/적립 내역에 요율 대신 **"150% 적립" 배수 배지**만 노출. 계산식 은닉.

  - **사용 여부**: 카드별 사용(Redeem) 여부는 Giftronaut `recipient.redeemed` 웹훅(**제공 예정**)이 있어야 확인 가능 — 그 전까진 "확인 불가"로 표시 → 사용·미사용(소멸) 금액 리포트 제공 여부를 Giftronaut에 확인(질문 10)
  - 고객 화면엔 내부 사유(API 코드·Balance 부족) 비노출 — 일반 문구만, 사유는 감사 로그에만
- **W-9(미국 세무)**: 미국 수령자용. 비USD Branded는 비대상, Choice(USD)는 집계되나 미국인에게만 요청 → **기능 OFF 유지**, 국내 세무 처리는 별도(§4.3 확인 필요 ④).

**Production 전환 체크리스트**: ① 포털 Production App 생성 ② **서버간 접근 요청 — ELLIS 서버 egress IP(CIDR) 허용목록 필수**(누락 시 403) → 승인 후 client_credentials ③ 웹훅 엔드포인트 등록(HTTPS 공개, `challengeToken` 응답) + 서명 secret 보관 ④ OMH 로고 이메일 템플릿 ⑤ Balance 충전(Wire) ⑥ 주문 한도 증액 ⑦ 사업자 서류. **결제 담당 계정(청구 계정)에서 App을 만들어야 함**(자격증명 이전 불가).

#### 멤버리스트 폐기 — 재사용 자산 (재론 대비 보존)

프로토타입에서 시험했으나 폐기된 개념. 다시 논의될 경우 출발점:

1. **두 계정 모델** — ⑴ Direct(고객사 직영 OP) ⑵ Shop-in-Shop(메인 아이디 아래 새끼 업체에 OP 아이디 배분 — 같은 사업자 아님). 실사이트 Member list는 직영만 전제.
2. **예약 귀속 = OP 아이디** — 샵인샵에서 누구 예약인지는 OP 아이디로 식별.
3. **바우처 잠금**(중국 업체 아이디어) — 예약자만 바우처를 열 수 있게 PIN 요구. 같은 포털의 다른 새끼 업체가 남의 바우처를 못 보게 격리. **미해결 설계점: PIN 단위** — OP 단위 vs 예약 건별(현업 예시는 "이 예약 건 오픈할 때 비번"이라 건별에 가까움).
4. **실물화 전제** — 이 개념은 결국 **Bookings 목록·바우처 발행 흐름**과 붙어야 실동작. 프로토타입은 핵심 예약 화면을 건드리지 않고 Staff 화면 안에서 시연만 했음.
